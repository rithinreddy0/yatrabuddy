# YatraBuddy audit and first improvement batch (November 2026)

This records what the application does today, what was fixed in this batch, how it was
verified, and what should come next. The refinement brief covers 22 phases; this batch
handled the P0 items that most affect the core planning workflow. Everything else is
listed with a priority below rather than partly built.

## Architecture (as found)

- **Frontend:** React 19 and Vite 8 single-page app with hash routing (`src/App.jsx`).
  Features are in `src/features`, shared controls in `src/components`, and styling in
  nine global stylesheets, about 310 kB of CSS before gzip.
- **Backend:** FastAPI (`backend/main.py`) with SQLAlchemy (SQLite locally, PostgreSQL in
  production). The middleware applies Firebase Google sign-in, a same-origin check on
  writes, and per-route rate limits.
- **Chat:** `backend/planning_agent.py` streams NDJSON turns (`tool`, `delta`, `done`
  events) to `src/features/PlanningAgent.jsx`. It runs without an LLM key using public
  sources (GeoNames, Wikivoyage, Wikipedia, OpenStreetMap, Open-Meteo, OSRM). Groq and
  Gemini are optional.
- **Itinerary:** places are gathered (`live_place_research`), ranked
  (`trip_intake.ranked_places`), then grouped into days with OSRM drive times
  (`nearby.prepare_draft`).
- **Persistence:** the user library (trips, drafts, saved places, profile) is a single
  revisioned JSON document per user with optimistic concurrency (`/api/library`). Shared
  trip workspaces have their own tables.

## Changes in this batch

### Itinerary quality (backend)
- `live_place_research` now always queries curated attraction listings for the base town
  (within 25 km) **and its parent region** (within 45 km), not only when map results are
  sparse. A base town picked inside a region (Mapusa in Goa) now draws on the region
  guide: Basilica of Bom Jesus, Goa State Museum, Miramar Beach, Salim Ali Bird
  Sanctuary, a Mandovi river cruise.
- `ranked_places` weighs source quality. Wikivoyage and Wikipedia listings get +12, bare
  map tags with no description, photo, rating or website get −8, chain fast-food outlets
  get −30, generic cinemas and malls get −20, and stops more than 25 km away get −6 and
  are labelled "A day trip from your base (N km)".
- Numbered segments of one feature ("… – Stretch 1", "… – Stretch 5") are collapsed into
  a single stop.
- Place questions recognise "stays", "homestays", "accommodation", "guesthouses",
  "lodging", "beaches", "street food" and similar words. When several categories appear,
  the first one named is the subject ("restaurants near the hotel" means food).
- A lookup that finds nothing for "Calangute beach" retries as "Calangute". The retry
  strips trailing landmark words such as beach, area, station and market.

### Chat (frontend)
- The fixed 25-second cap on the entire streamed turn is replaced with a **30-second
  idle timeout** that resets on each chunk, plus a 120-second hard cap. Long but
  healthy answers are no longer cut off.
- **Stop** re-syncs with the server. If the server had already saved the turn, the
  saved reply is shown. Otherwise the user sees "Response stopped before it finished.
  Nothing from it was saved." with a **Retry** button. Before this change, a retry after
  a late stop failed with a version conflict.
- Network and server failures on a message now offer **Retry**.
- Each itinerary stop shows **"Why this stop"**, using the ranker's existing reasons
  ("Listed in the Wikivoyage guide", "A day trip from your base (37 km)").
- The header title keeps the region ("Trip to Mapusa, Goa").
- Shorter composer placeholders stop the textarea growing to three lines on phones.

### Mobile and loading
- At 560 px and below, chat header actions are 40 px icon buttons with accessible
  names, and the title truncates to one line.
- The bottom dock is hidden **when an on-screen keyboard is open** (detected with
  `visualViewport`, see `src/viewport.mjs`), instead of whenever the composer has focus.
- On touch screens, standalone links (provider "Open …" pills, source icons, weather
  chip, itinerary stop titles) have a hit area of at least 36–40 px.
- Route changes still move focus to the page heading for screen readers, but no longer
  draw a focus ring around the title.
- The startup splash disappears as soon as the app renders. In the production build the
  app was interactive about 150 ms after navigation (warm cache), compared with a
  previous minimum of 1.53 s.

## Verification

All results below come from runs in this environment on 2026-11-14.

- **Backend unit tests:** 89 passed. That is the 83 existing tests plus 6 new ones in
  `backend/test_ranking_quality.py`.
- **Frontend unit tests:** 10 passed. That is the 8 existing tests plus 2 new ones in
  `src/viewport.test.mjs`.
- **Production build:** succeeds.
- **Browser, horizontal overflow:** a script measured overflow on Home, Chat, My Trips,
  Explore, Saved, Destination guide, Preferences, Travel desk and the demo itinerary at
  320 px, 360 px, 768 px and 1280 px. No page scrolled horizontally at any width.
- **Browser, full trip flow at 360 px:** "I want to visit Goa for three days" → 2
  travellers → Hyderabad → ₹20,000 → Mapusa produced the improved itinerary. A
  single-message trip request built a plan with no follow-up questions.
- **Browser, failure paths:** Stop mid-turn showed the notice, nothing was saved, and
  Retry completed. When the API was unreachable, an error with Retry appeared.

Not verified: real-device keyboard behaviour on iOS or Android (the emulator has no
on-screen keyboard), landscape layouts, and flows that need credentials (Google sign-in,
Groq or Gemini, Google Places, Booking.com, Amadeus).

## Local setup notes

- `.claude/launch.json` defines `api` (FastAPI on 8000), `web` (Vite on 3000) and
  `web-prod` (built app on 3010).
- A local `.env` (git-ignored) sets `REQUIRE_GOOGLE_SIGN_IN=0` so flows can be tested
  without Firebase. Do not use that setting in a deployed environment.
- On Windows, uvicorn's `--reload` sometimes stalls after an edit. Restart the API if
  responses look stale.

## Recommended next priorities

1. **Budget tracking for real trips (P1).** Add planned-vs-actual expenses with category,
   payer and date to the trip document, a remaining-budget forecast, and a settlement
   summary. Keep estimates, confirmed bookings, actual spend and refunds as separate
   ledgers so nothing is counted twice. The `Yatra.jsx` demo already has a UI to start
   from.
2. **Meal placement (P1).** Search food near each day's cluster of stops, not only near
   the base town.
3. **Destination guide content order (P1).** Lead with best season, typical length,
   budget range, getting there and top sights. Move licence detail into source
   disclosures.
4. **Bookings outside shared workspaces, with explicit states (P2).** Opening a provider
   link must never mark a booking confirmed.
5. **Route-level code splitting (P2).** Reduce the 706 kB main chunk.
6. **Merge the Explore "Hotels" and "Stays" filters (P2).**

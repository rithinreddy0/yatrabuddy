# YatraBuddy audit and first improvement batch (November 2026)

This records what the application does today, what was fixed in this batch, how it was
verified, and what should come next. The refinement brief covers 22 phases; this batch
handled the P0 items that most affect the core planning workflow. Everything else is
listed with a priority below rather than partly built.

## Architecture (as found)

- **Frontend:** React 19 and Vite 8 single-page app with hash routing (`src/App.jsx`).
  Features are in `src/features`, shared controls in `src/components`, and styling in
  nine global stylesheets, about 310 kB of CSS before gzip.
- **Backend:** FastAPI (`backend/main.py`) with SQLAlchemy (SQLite locally, PostgreSQL in
  production). The middleware applies Firebase Google sign-in, a same-origin check on
  writes, and per-route rate limits.
- **Chat:** `backend/planning_agent.py` streams NDJSON turns (`tool`, `delta`, `done`
  events) to `src/features/PlanningAgent.jsx`. It runs without an LLM key using public
  sources (GeoNames, Wikivoyage, Wikipedia, OpenStreetMap, Open-Meteo, OSRM). Groq and
  Gemini are optional.
- **Itinerary:** places are gathered (`live_place_research`), ranked
  (`trip_intake.ranked_places`), then grouped into days with OSRM drive times
  (`nearby.prepare_draft`).
- **Persistence:** the user library (trips, drafts, saved places, profile) is a single
  revisioned JSON document per user with optimistic concurrency (`/api/library`). Shared
  trip workspaces have their own tables.

## Changes in this batch

### Itinerary quality (backend)
- `live_place_research` now always queries curated attraction listings for the base town
  (within 25 km) **and its parent region** (within 45 km), not only when map results are
  sparse. A base town picked inside a region (Mapusa in Goa) now draws on the region
  guide: Basilica of Bom Jesus, Goa State Museum, Miramar Beach, Salim Ali Bird
  Sanctuary, a Mandovi river cruise.
- `ranked_places` weighs source quality. Wikivoyage and Wikipedia listings get +12, bare
  map tags with no description, photo, rating or website get −8, chain fast-food outlets
  get −30, generic cinemas and malls get −20, and stops more than 25 km away get −6 and
  are labelled "A day trip from your base (N km)".
- Numbered segments of one feature ("… – Stretch 1", "… – Stretch 5") are collapsed into
  a single stop.
- Place questions recognise "stays", "homestays", "accommodation", "guesthouses",
  "lodging", "beaches", "street food" and similar words. When several categories appear,
  the first one named is the subject ("restaurants near the hotel" means food).
- A lookup that finds nothing for "Calangute beach" retries as "Calangute". The retry
  strips trailing landmark words such as beach, area, station and market.

### Chat (frontend)
- The fixed 25-second cap on the entire streamed turn is replaced with a **30-second
  idle timeout** that resets on each chunk, plus a 120-second hard cap. Long but
  healthy answers are no longer cut off.
- **Stop** re-syncs with the server. If the server had already saved the turn, the
  saved reply is shown. Otherwise the user sees "Response stopped before it finished.
  Nothing from it was saved." with a **Retry** button. Before this change, a retry after
  a late stop failed with a version conflict.
- Network and server failures on a message now offer **Retry**.
- Each itinerary stop shows **"Why this stop"**, using the ranker's existing reasons
  ("Listed in the Wikivoyage guide", "A day trip from your base (37 km)").
- The header title keeps the region ("Trip to Mapusa, Goa").
- Shorter composer placeholders stop the textarea growing to three lines on phones.

### Mobile and loading
- At 560 px and below, chat header actions are 40 px icon buttons with accessible
  names, and the title truncates to one line.
- The bottom dock is hidden **when an on-screen keyboard is open** (detected with
  `visualViewport`, see `src/viewport.mjs`), instead of whenever the composer has focus.
- On touch screens, standalone links (provider "Open …" pills, source icons, weather
  chip, itinerary stop titles) have a hit area of at least 36–40 px.
- Route changes still move focus to the page heading for screen readers, but no longer
  draw a focus ring around the title.
- The startup splash disappears as soon as the app renders. In the production build the
  app was interactive about 150 ms after navigation (warm cache), compared with a
  previous minimum of 1.53 s.

## Second batch (2026-11-14, after pulling `main` at `eabdd28`)

### Budget and expenses (Phase 11)
- `src/features/budgetLedger.mjs` holds all arithmetic; `TripBudget.jsx` is the screen under a saved trip's
  **Budget & expenses** section. The ledger is stored on the trip (`WorldwideDraft.ledger`, validated by
  `TripLedger` in `backend/models.py`), so it syncs with the library like the rest of the trip.
- Dashboard: total budget, expected trip cost, spent so far, remaining budget, still to pay, expected
  balance. The heading changes for before, during and after the trip.
- Separate ledgers so nothing is counted twice: logged expenses and refunds are *spent*; confirmed
  bookings nobody has logged as paid are *booked*; category budgets or stop entry costs are the *plan*.
  An expense can be linked to a confirmed booking, which then stops counting as booked.
- Splits are worked out in paise and settled with the fewest transfers. CSV export guards against
  spreadsheet formulas. A refund recorded on a cancelled booking can be added to spending with one click.

### Bookings (Phase 12)
- Booking entries have a status (suggested, booking link opened, pending confirmation, confirmed,
  cancelled, refunded), a type, a reference/PNR and a refund amount, validated in `trip_workspace.py`.
- New bookings default to *pending*. Only confirmed bookings count in the budget. Transport provider
  options can be saved as a *suggested* booking; opening a provider page never confirms anything.
- Bookings saved before this change show "Status not set" and are not counted until a status is chosen.

### Destination guide, Explore and updates (Phases 6–8)
- New `/api/climate` (`backend/climate.py`) summarises 2023–2025 daily records from the Open-Meteo
  historical archive into monthly temperature, rainfall and wet days, and picks the most comfortable
  months. It is labelled as past weather, not a forecast. Goa returns Nov–Apr with heavy rain May–Oct.
- The guide's **Trip essentials** panel shows that, a suggested length (labelled as a YatraBuddy
  suggestion and based on how many sights are listed nearby), sample stay prices where the catalog has
  them, and a getting-there box that hands the route to the chat.
- Updates keep only travel-relevant stories. Political, crime, market and sports headlines are dropped
  unless they report a disruption (bandh, strike, closure, suspension). Disruptions come first and every
  story says what the traveller should do.

### Planning, transport and performance
- Meals: the planner looks up food near distant clusters of likely sights and reserves the best nearby
  option for each cluster. In a live Mapusa run, the Panaji and Vasco days got lunch beside their sights
  instead of driving back to Mapusa. When there are more distant clusters than meal slots, the remaining
  day can still use a base-town meal.
- Itinerary stops show "YatraBuddy match N/100" next to the reasons, labelled as an internal fit score and
  not a public rating.
- Transport results can be ranked by best overall, cheapest, fastest or fewest changes. Ranking uses only
  fares, durations and legs the providers returned, refuses to compare mixed currencies, and explains each
  position.
- Route components are lazy-loaded; the main chunk fell from 706 kB to 338 kB.

### Verification (batch 2)
- Backend: 103 tests pass (new: `test_budget_bookings.py`, `test_climate.py`, `test_news_relevance.py`,
  meal placement in `test_ranking_quality.py`). Frontend: 18 tests pass (new: budget ledger and transport
  ranking). Production build succeeds.
- In the browser at 360 px: set a budget plan, logged two expenses, saw a correct settlement (Asha pays
  Ravi ₹1,900), added a confirmed train booking and saw it counted once as booked, then offered for linking.
  Guide essentials rendered with live climate data. No page scrolled horizontally on Home, Chat, My trips,
  Explore, Stays, Saved, Guide, Preferences, or a saved trip's itinerary, budget, bookings and transport.
- Not verified: the ranked comparison with real provider data (needs `DUFFEL_ACCESS_TOKEN` or
  `GOOGLE_ROUTES_API_KEY`), receipt uploads on expenses (not built; booking receipts already exist), real
  devices, and signed-in sync. Public place sources still time out now and then; when the regional
  guide lookup fails, a trip falls back to local map listings.

### Still open
1. Receipt attachments on expenses, and expenses for guests across devices (they stay in the browser).
2. Live events listings (festivals, concerts) from a dated source; today only news mentions them.
3. Day-level regeneration ("redo day 2") as one action in the itinerary.
4. Departure and check-in reminders driven by booking dates.

## Third batch: trip Transport redesign (2026-11-14)

### Problems found
- The tab was about 2,750 px tall on a phone and opened with an empty form, although the trip already knew
  the departure city, date and travellers.
- It never answered the basic questions: how far, how long by road, which airport or station is nearest.
- Five provider cards each said "enter your cities and date"; "Pin to compare" added nothing.
- Local travel showed one leg at a time from a dropdown of every leg, plus a large map, even though the trip
  already stores distance and time for each leg.

### What changed
- New `GET /api/trip-transport` (`backend/trip_transport.py`): resolves the departure city, returns the OSRM
  road distance and time, the straight-line distance, and the nearest commercial airports (with IATA codes)
  and mainline railway stations (with station codes) around the stay and the departure city. Data comes from
  OpenStreetMap through Photon and one batched OSM API call; metro stops, stations under construction and
  military airfields are filtered out. Results are cached for a week.
- The Transport tab (`TripTransport.jsx`, helpers in `tripTransportPlan.mjs`):
  - opens with the route prefilled from the trip, a "Change" form that only affects the view, and an
    "Add a date" prompt;
  - shows road distance, drive time, straight-line distance and general guidance by distance;
  - has Fly / Train / Bus / Drive tabs. Phones show one at a time, preselected by distance; wider screens
    show all four. Each lists the real arrival points with codes and distance to the stay, and opens
    prefilled searches: Google Flights for each airport pair and date, erail.in's list of trains between the
    two station codes, IRCTC, redBus/AbhiBus, and directions from the airport or city to the stay;
  - estimates one-way fuel cost from the traveller's own mileage and fuel price (stored in the browser), split
    per traveller, with tolls and parking excluded and the assumptions stated;
  - saves any option to Bookings as a *Suggested option*;
  - shows live offers and the ranked comparison when Duffel or Google Routes are configured;
  - lists every day's journeys with distance, time, a suggested mode (walk, auto or cab, cab, or bus/metro
    when preferred), a directions link and an on-demand public transport lookup.
- The tab is about 1,670 px tall on a 390 px phone, down from 2,750 px.

### Verified
- Hyderabad → Mapusa: 658 km and about 8 h 29 min by road, 534 km straight line; airports GOX (17 km from the
  stay) and GOI (24 km); stations Thivim (THVM, 8 km) and Karmali (KRMI); departure HYD and Hyderabad Deccan (HYB).
  London → Paris also resolves. An unknown city shows a clear message.
- Setting a date updates the flight links; saving the train option created a Suggested booking; the public
  transport lookup reported that no scheduled service was found for a Goa leg.
- 105 backend and 24 frontend tests pass; build succeeds.

### Limits
- Without Duffel or Google Routes credentials there are no fares or timetables in the app; the links open
  provider searches instead. erail.in and the Google Flights query links depend on those sites keeping their
  URL formats. redBus cannot be prefilled.
- Station lists near large cities include small halts; the card asks travellers to check which station their
  train uses.

## Local setup notes

- `.claude/launch.json` defines `api` (FastAPI on 8000), `web` (Vite on 3000) and
  `web-prod` (built app on 3010).
- A local `.env` (git-ignored) sets `REQUIRE_GOOGLE_SIGN_IN=0` so flows can be tested
  without Firebase. Do not use that setting in a deployed environment.
- On Windows, uvicorn's `--reload` sometimes stalls after an edit. Restart the API if
  responses look stale.

   payer and date to the trip document, a remaining-budget forecast, and a settlement

   ledgers so nothing is counted twice. The `Yatra.jsx` demo already has a UI to start
   from.

   the base town.

   disclosures.

   link must never mark a booking confirmed.
